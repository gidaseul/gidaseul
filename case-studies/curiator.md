## 문제와 담당 범위

같은 작품이라도 어린이에게는 쉬운 표현이, 전문가에게는 작품의 맥락과 용어가 필요합니다. 여기에 해설 언어까지 달라지면 작품 정보를 여러 번 편집하게 됩니다. 저는 작품·챕터 입력을 해설 생성과 음성 합성에 연결하는 AI API를 맡았습니다. 공개 저장소에는 이후 정리한 전시 자료 검색과 해설 편집 화면도 포함돼 있습니다.

## 해설을 먼저 고치고 음성을 만드는 흐름

1. 작품이나 챕터 JSON을 입력하면 FastAPI가 공통 형식으로 변환합니다. 전시 자료 검색을 켜면 관련 작품과 챕터를 함께 찾아 Gemini에 전달합니다.
2. `POST /generate-text`가 이야기 중심 해설과 역사·정석 해설을 반환합니다. 웹 화면에 검색한 참고 자료도 표시합니다.
3. 관람객은 한 해설을 골라 문장을 편집합니다. `POST /generate-audio`는 편집한 문장만 받아 Gemini TTS로 읽어 줍니다. 글을 고친 뒤 음성을 만들 수 있도록 두 요청을 분리했습니다.

## 작품 하나로 보는 생성 과정

다음은 화면의 사용 순서를 보여주는 예시입니다. 전시 담당자가 도자기 작품의 이름, 제작 시기와 재료가 들어 있는 JSON을 준비한 뒤 한국어와 어린이 수준을 고릅니다. 여러 작품이 묶인 챕터를 넣는 경우에는 선택한 챕터와 그 안에 포함된 작품 정보를 묶어 해설의 입력으로 사용합니다. 작품 하나와 챕터 입력을 서버에서 공통 형식으로 변환해 같은 생성 흐름에 연결했습니다.

이야기 중심 해설에서는 작품의 생김새를 먼저 관찰하도록 유도할 수 있고, 역사·정석 해설에서는 제작 시기와 재료부터 소개할 수 있습니다. 화면에서는 두 초안을 나란히 보고 한쪽의 어려운 단어나 발음하기 까다로운 표현을 고친 뒤 음성을 요청합니다. 최종 편집 문장이 음성 API의 입력이므로 오디오를 만들 때 모델이 해설을 다시 쓰는 단계가 없습니다.

해설 생성과 음성을 분리하면 초안을 여러 번 다듬은 뒤 필요한 문장만 읽을 수 있습니다. 음성 합성에 오류가 생겼을 때도 이미 작성한 해설을 다시 생성할 이유가 없습니다. 프로젝트의 화면은 작품 입력, 해설 편집, 재생 순서로 구성돼 이 경계를 드러냅니다.

## 파일 구조와 API

```text
Curiator/
├── frontend/src/steps/   작품 입력, 수준 선택, 해설 편집, 오디오 재생
├── main.py              해설·오디오·전시 질문 API
├── museum_source.py     작품·챕터 데이터를 공통 형식으로 변환
├── llm/generate_docent.py  해설과 질문 답변 프롬프트
├── rag/store.py         검색 점수, 결과 선별, 어휘 검색 대체 경로
├── tts/generate_tts.py  Gemini 음성 생성
└── tests/              외부 API 없이 검증하는 입력·검색·응답 테스트
```

| 요청 | 주요 입력 | 확인할 응답 |
| --- | --- | --- |
| `POST /generate-text` | 작품 또는 챕터, 언어, 관람객 수준, 자료 검색 여부 | 해설 두 가지, 참고 자료 목록 |
| `POST /generate-audio` | 편집한 해설, 언어, 목소리 | 생성한 음성 파일 URL |
| `POST /ask` | 관람객 질문과 언어 | 답변, 참고 자료, 검색 근거 여부 |

## 검색 근거를 어디까지 믿을 수 있나

전시 자료를 작품과 챕터 단위로 나눠 검색합니다. 임베딩 검색을 쓸 수 있으면 코사인 유사도 0.55 이상을 남기고, 임베딩을 쓸 수 없으면 문자 묶음 기반 TF-IDF 검색으로 전환해 별도 기준인 0.08을 적용합니다. `references`의 검색 방식과 점수는 어떻게 자료를 찾았는지 확인하는 단서입니다. 서로 다른 검색 방식의 점수를 같은 척도로 비교하기는 어렵습니다.

`/ask`는 검색 기준을 넘는 참고 자료가 없으면 모델을 부르지 않고 안내 문구를 돌려줍니다. `grounded: true`는 참고 자료를 찾아 프롬프트에 전달했다는 뜻입니다. 답변의 개별 문장이 자료와 일치하는지 확인하는 검증 단계는 별도입니다.

같은 도자기에 대해 “어떤 재료로 만들었나요?”라는 질문이 들어오면 작품 설명이나 관련 챕터 중 검색 점수가 기준을 넘는 문서를 먼저 찾습니다. 질문에 답할 만한 문서가 검색되지 않은 경우와 참고 자료를 확보한 뒤 모델 호출이 실패한 경우는 서로 다른 경로입니다. 전자는 자료가 없다는 응답을 내고, 후자는 생성 오류를 반환합니다. 전시 자료를 보충해야 하는지, 생성 요청을 다시 보내야 하는지 판단할 때 이 구분이 필요합니다.

## 검증 결과와 실행 경로

통합 작업에서 외부 API 없이 실행하는 테스트 19개와 프런트엔드 빌드를 확인했습니다. 테스트는 입력 형식, 검색 결과 처리, 근거가 없을 때의 응답을 확인합니다. 실제 Gemini를 연결한 실행과 해설 사실성·음성 품질은 별도 검증 범위입니다.

현장용 검증에서는 동일 작품의 해설을 언어와 관람객 수준을 바꿔 생성하고, 작품명·제작 시기·재료가 원자료와 일치하는지 따로 확인할 수 있습니다. 이어서 고유명사를 편집해 음성에 반영되는지 듣고, 자료에 없는 질문에서는 안내 응답이 나오는지 봅니다. 이 세 확인으로 입력 자료의 사실 보존, 텍스트 편집과 음성의 연결, 질문 응답의 검색 경계를 따로 평가할 수 있습니다.
